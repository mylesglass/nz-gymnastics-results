**Known issues:**
- The remaining same-ID-different-people cases that are *in the source data itself* (e.g. `252164` = Arden + Daniel) are kept separate by the `athletes` identity table (shared ID + dissimilar names ⇒ distinct athletes). Manual review of these (and same-name duplicates) is now tooled: the admin Identity Review card lists every ID/name conflict with per-athlete evidence and provides Merge/Split — see `GET /api/admin/identity-review`.

**Previously fixed:**
- Inline-edit saves still showed the OLD value in the table even after the DB was correct (reported twice: Abigail Bell, Bella Small). Root cause was a **race between the edit's synchronous store refresh and the background full rebuild**: `rebuild_event` silently skipped when the full rebuild held the rebuild lock, and the in-flight rebuild (which had read the *pre-edit* data) then wrote the stale value into the store — so the table kept showing the old division until the next ~20–50s rebuild finished. Fix: mutations flag their event **dirty** (`mark_event_dirty` via `cache.invalidate`), and the wide read endpoints refresh any dirty event's store rows on demand (`rebuild_event`, ~0.4s) — or live-pivot that event when a full rebuild is mid-flight — so a just-saved edit is never hidden by stale prebuilt rows. A completed fresh `rebuild_all` clears the dirty set. Regression tests: `TestEditDuringInFlightRebuild` in `test_admin_edit.py` (edit/reload during a held lock, live-pivot during a held lock, wide-all freshness, dirty-set lifecycle). Also fixed a latent `_replace_store` crash when a store (e.g. `wellington_cache`) was empty (0 bindings for 2 placeholders).
- Inline edit (name/GNZ ID/club) saved to DB but the table didn't feel reactive: the materialized `wide_rows` store stayed stale until the async full rebuild (~34–49s) **and** the 300s `Cache-Control` on the wide endpoints made the browser serve its old cached copy for up to 5 minutes. Now the edit endpoint synchronously refreshes the edited event's store rows (`rebuild_event`), the post-save reload bypasses the browser cache (`fetch cache: "no-store"`), and the reload preserves the current tab/search/filters/sort/page instead of resetting to WAG page 1. **The wide endpoints (`/api/events/{id}/results/wide`, `/api/results/wide-all`) now return `Cache-Control: no-store` outright** — a browser-cached copy hid a freshly-saved division edit from the table even after the store was correct (reported twice); they read the cheap materialized store, so always-fetch costs nothing. Also extended to edit division + round-type (scoped by the currently-displayed value so a round rename can't rewrite the athlete's other rounds) and scoped by `slug` so two same-name athletes in one event edit independently. Tests: `backend/tests/test_admin_edit.py` (10 cases).
- Inline edit saves were very slow (~17s) because the endpoint ran the **full-DB athlete re-cluster** (`rebuild_athletes`, ~6s+) synchronously on every save — even for a division/round-type edit, which can never change a cluster. Now `rebuild_athletes` only runs when name/GNZ ID/club change; division/round saves complete in ~0.1s, and the row's Save button shows a spinner while an identity edit re-clusters.
- Inline name/GNZ ID edits were **silently reverted** by the identity layer: the PATCH was event-scoped, so if the gymnast had more rows under the old spelling/ID in *other* events, `rebuild_athletes`'s majority-canonical back-write restored the old value everywhere. Name/GNZ ID edits (with a slug) now propagate to **every row of the athlete across all events**, so a fix wins the majority. Regression test: `test_name_edit_propagates_across_events`.
- Gymnast Personal Bests card ignored *all* `Apparatus Finals` / `Day 2` round-types when computing the best achieved AA, even when the gymnast completed a full all-around that day — a genuine season-best finals-day total (e.g. Vita Ede's HBPB 2026 apparatus-finals 56.625) was dropped and her second-best shown. `SeasonBest.svelte` now counts finals/day-2 rows **only when the row has a complete apparatus set** (every `{p}-total` present); partial finals-day sums still never masquerade as an AA.
- Level/division mislabeled when a gymnast is registered against result tables they never scored in: `parse_json` derived `level_category`/`division` from the **first** `performanceIndividual.resultTableConfigs` entry whose node name resolved to a level, trusting config order over actual results. In CSG 2026 the source registered STEP 10 gymnast Claudia Renaud against `Senior International` tables **first** (she never scored in them — all her `performanceResultTables` rows are STEP 10), so she was stored as `Senior International`. Fix: the level/division now comes from the first config **backed by an actual published result** (the entity appears in that table's `primaryRanking`), falling back to the old first-config behaviour, with division taken from the same node that determined the level (so a stale `INTERNATIONAL` registration division can't leak onto a STEP gymnast). Verified across all 2022–2026 source files: the only changed entity is Claudia Renaud (`Senior International` → `STEP 10`, division `None`). Regression test: `test_csg_classic_step10_not_mislabeled_as_international`. CSG 2026 re-uploaded to the dev DB to fix the stored rows.
- `repair_identities.py` v1 trusted each source file 100% per-event, so a single file's typo could overwrite a consistent DB ID (e.g. `Alexandra Boys` → 7-digit `6511229`, or near-ties like `emily crisp` 2:3). Diffing the result against a per-(name, club) source consensus exposed 1,016 of 1,787 ID changes moving *away* from consensus. Rewritten to be **consensus-driven**: majority ID across all source files per `(name, club)`, winner must beat runner-up ≥2x; verified the corrected end state has 0 rows differing from consensus.
- Name mangling: `_clean_name` used `w.capitalize()` which lowercased internal caps (`Eva McEwan` → `Eva Mcewan`). Fixed with `_title_case_token` that preserves tokens with an internal uppercase letter; existing rows repaired via `python -m app.repair_identities`
- Destructive name-keyed reconcile: two different people sharing a name (e.g. two Madison Lynches at one event) were irreversibly merged into one GNZ ID after every upload. `reconcile_athletes()` is now evidence-based — same-event ID collision or discipline conflict → `conflicts` with a `reason`, never merged
- Ingest backfill assigned missing IDs by name even when the name mapped to multiple IDs — now only backfills when a name maps to exactly one distinct numeric ID
- Bulk URL upload: events with unknown clubs vanished after Save & Retry — during a batch URL import, any event that opened the unknown-club dialog and was resolved via *Save & Retry* (or *Keep all original*) disappeared from the upload list.
